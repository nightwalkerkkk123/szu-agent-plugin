## Friction

- **用户现场反馈比单测更准**: 我自己写完 `SelectDateStep` 后跑了一次真实环境,**没成功**(label 找不到),但当时我把锅扣给"硬编码日期"。你看到日志后问"日期不该硬编码因为每天都会变" — 我这才意识到我已经误读了真实 DOM 形态(以为 label 跟"今天"文字绑定,实际是 `for=YYYY-MM-DD`)。**用户的提问把诊断方向拉回正确位置**。Lesson: 修复时把"假设/我以为"先列出来,再去找证据,不要凭想象写 selector。

- **diagnostic dump 工作流值得保留**: 我在 `execute()` 入口插了一段 `browser.evaluate()` 把所有 label/input 的 `for/id/text` 打印到日志,目的是看真实 DOM 长什么样。**虽然最终没用到这个 dump**(你直接贴了 HTML),但这种"在生产代码加一次性探针→跑一次→看真实 DOM→撤掉"是 web scraping 类工具的高 ROI 习惯。**建议**把"探针 dump"做成 `BrowserLifecycle` 的 `dumpDom(String tag)` 方法,在 harness 调试时启用,长期收益高。短期没做,记入 HARNESS_BACKLOG。

- **Playwright isVisible 的隐式假设**: 我假设 `isVisible(selector)` 给出"label 是否在 viewport 内" 的布尔,实际上 Playwright 的 visibility 判定还考虑**父链、display 链、可见性祖先**。`display:none` 的 input 不会让父 label 不可见,但 `isVisible('label[for=...]')` 内部评估时把"目标元素可见性"和"目标元素本身是否真的在 DOM"混淆了 — 实际行为是"label 不可见"。**根因**: Playwright 把 label 当成 radio 的可视代理,label 上无视觉内容(纯 wrapping) 时报不可见。Lesson: Playwright 的 visibility 判定对 `display:none` 包裹的元素链,行为不是直觉;用 `click()` + actionability 更稳。

## Harness Improvement

**Pain:** 真实 run 才能发现 selector bug,但用户每次授权有摩擦(auto-mode classifier 拦"真实预约")。从"代码改完"到"看到真实 run 失败信号"的反馈环太长(打包 + 启动 + 等待登录)。

**Proposal:** 加一个 `--smoke` 模式,只跑 CAS_LOGIN + NAVIGATE_TO_BOOKING + SELECT_CAMPUS + SELECT_SPORT,**不到 SELECT_DATE**;跑完截图 + 退出。这样可以在不进入"预约事务"的前提下验证 4 个 selector,**不触发 auto-mode classifier 的"real booking"拦路**。记入 HARNESS_BACKLOG。

## Decisions Made

- **D1**: 不再 `isVisible` 预检。理由: `click()` 内部已有 actionability check(等可见、等稳定、等可点击),外层 isVisible 既冗余又不准(对 `display:none` 包裹的 label 误判)。**KISS**。
- **D2**: 不在 production 代码保留 diagnostic dump(已撤掉)。理由: 这是一次性探针,长期保留会污染日志。改写进 HARNESS_BACKLOG 作为未来 feature。
- **D3**: 测试断言"selector 反映 `request.date()`"取代"label 不可见返回 Failure"。理由: 旧测试断言的行为(isVisible+click)已不存在,新测试断言的是**真正重要的不变式 — selector 永远从 request 算出,不是 hard-coded**。
