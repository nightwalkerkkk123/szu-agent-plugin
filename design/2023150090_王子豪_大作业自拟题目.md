## 一、题目背景与动机

### 1.1 现状

深圳大学内部网(ehall、CAS、企业微信、畅课)上存在大量**重复、固定、流程化**的操作:体育场馆预约、公文通查询、畅课作业查看、成长方案进度、邮件草稿生成。学生每周要重复点击数十次,典型如**网球场抢订**(每天 20:00 准时开放下一日预约,手速慢即无场地)。

与此同时,2025 年起 ChatGPT Agent / Claude Code / OpenClaw 等 **AI Agent 平台**逐步开放第三方工具调用接口(MCP / Skill 协议),允许学生用自然语言指令驱动本地工具完成任务(如"帮我抢明晚 8 点网球场")。

### 1.2 问题

- 现有 AI Agent **不知道**深圳大学内部网的页面结构、登录流程、字段名
- 学生不可能为每个 Agent 平台单独写一份调用代码
- 直接给 Agent 暴露浏览器自动化能力又有安全风险(密码泄漏、绕过验证)

### 1.3 解决思路

**把校园流程封装成可被 AI Agent 调用的标准化工具**:

- 用 **Java CLI** 作第一性工作单元,接收结构化参数(`--campus YUEHAI --sport TENNIS --date 0`),返回 JSON 结果
- 用 **Playwright** 在用户本地浏览器执行实际操作,**密码、Cookie 永远不离开本机**
- 提供 **Skill / MCP 薄壳** 让外部 Agent 通过协议调用本 jar
- 用 **重试策略 + 错误码元数据** 提高真实场景下的可靠性

### 1.4 个人价值

- 解决自身真实痛点(我自己每周三抢网球场)
- 学习并落地"面向对象高级编程"课程要求的 4 种设计模式 + 6 种编程技术(经 ADR-0007 D1 确认 4 模式自然落地优于硬塞 5 种)
- 体验"工具型 Java 项目"的完整工程实践(Maven Shade、JaCoCo、ArchUnit、JUnit 5、Logback、picocli)

## 三、设计模式落点(4 种,经 ADR-0007 D1 从 5→4 收敛)

> 显式标注约定:每个核心类**首行注释**包含 `// Design Pattern: XXX`,教师可直接 `grep -r "Design Pattern" src/main/java` 验证。
>
> **为何只取 4 种**:ADR-0001 D9 + ADR-0007 D1 经审视确认 — 业务自然生长出的模式只有 4 种;
> 强行凑出第 5 种(原拟 BrowserFactory / Static Factory)会导致"3 行 switch、实现 ≈ 接口"的纸上模式,
> 违反"模式必须从业务真问题中浮现"原则。删除浅模式后,4 种模式每种都有 2+ 处真业务落地。

### 3.1 Builder 模式

| 位置 | 角色 |
|---|---|
| `domain.BookingRequest` | 产品(Java 21 record,不可变) |
| `domain.BookingRequest.Builder` | Builder(static final 内部类) |
| `cli.VenueCommand.call()` L141-148 | 指导者 |

**关键代码**:`build()` 集中校验 — 4 个必填字段非空 + `preferredVenueIndex >= 1`,失败抛 `IllegalArgumentException` 被 CLI 映射到退出码 2。

### 3.2 单例模式 (Singleton) — 双检锁

| 位置 | 用途 |
|---|---|
| `config.ConfigManager` | YAML + env-file + 进程 env 三层配置查找 |
| `observability.Tracer` | trace_id 生成 + MDC 注入 + 失败记录 |

**关键代码**:双检锁 + `volatile` 保证多线程可见性;`reset()` 包私有方法作为测试缝隙。

### 3.3 策略模式 (Strategy)

| 位置 | 实现数 |
|---|---|
| `matcher.Matcher<T>` (`@FunctionalInterface`) | 5 种实现(Exact / Contains / Regex / VenueIndex + AbstractMatcher 基类) |
| `retry.RetryPolicy` (`@FunctionalInterface`) | 3 种实现(NoRetry / FixedDelay / ExponentialBackoff) |
| `client.step.BookingStep` | 7 种实现(CasLogin / NavigateToBooking / SelectCampus / SelectSport / SelectTimeSlot / SelectVenue / ConfirmBooking) |

**关键代码**:三套都暴露 `of(...)` 静态工厂便于 Lambda 化构造;`Matcher` 提供 `and / or / negate` 默认方法做组合。

### 3.4 适配器模式 (Adapter)

| 位置 | 角色 |
|---|---|
| `browser.BrowserLifecycle` | 目标接口(10 方法) |
| `browser.PlaywrightBrowserAdapter` | 适配器(具体实现) |
| Playwright Java SDK | 被适配的对象 |

**关键代码**:Adapter 负责 Playwright 异常 → `ErrorCode` 映射(`TimeoutError → NETWORK_TIMEOUT`,选择器失败 → `ELEMENT_NOT_FOUND`,其他 → `BROWSER_CRASH`)。

### 3.5 架构模式说明 — 流水线 (Pipeline) 与 命令 (Command)

> 这两个**不计入主清单的 4 模式**,但课堂讲解时值得提及:

- **Pipeline**:`VenueBookingClient.book()` 串联 7 个 `BookingStep` 形成线性流水线,共享 `BookingContext`。
  这是 **Strategy 模式的架构应用**(每个 step 是一个 Strategy 实例),不是独立的 GoF 模式。
  `selectedVenue` 写在第 5 步、读在第 6 步,展示流水线状态共享设计。

- **Command**:CLI 通过 picocli 的 `@Command` 注解路由(`Main` → `BookingCommand` → `VenueCommand`)。
  这是 **picocli 框架的内建机制**,不是项目层面自己实现的 GoF Command 模式;因此代码注释不写
  `// Design Pattern: Command`,避免与 4 模式清单冲突(详见 ADR-0007 D1)。

## 四、编程技术落点(6 种)

> 显式标注约定:每处使用**首行注释**包含 `// 编程技术: XXX`。

### 4.1 泛型

- `Matcher<T>` —— `@FunctionalInterface` 通用谓词,实例化为 `Matcher<String>`
- `RetryPolicy.execute(Supplier<T>)` —— 重试包裹任意返回值的 Supplier

### 4.2 枚举(携带元数据)

- `error.ErrorCode` —— 12 个错误码,每个挂 5 字段元数据(`severity` / `retryable` / `switchAccount` / `screenshot` / `hint`),取代 Python 端 `ErrorClassifier` 类(ADR-0006)
- `error.Severity` —— 4 级严重度,序数即排序
- `domain.Campus` / `domain.Sport` —— 携带 `displayName` 中文 + `ehallCode` 线格式

### 4.3 注解

- `@Command / @Option / @Spec`(picocli)—— CLI 路由
- `@Test / @DisplayName / @Nested / @ParameterizedTest / @CsvSource / @TempDir`(JUnit 5)—— 测试
- `@FunctionalInterface` —— 三处函数式接口标记
- 自定义 `package-info.java` 类级 javadoc

### 4.4 重载(Overloading)

- `matcher.ContainsMatcher` —— 默认大小写敏感 + `boolean ignoreCase` 重载
- `retry.ExponentialBackoff` —— 简形构造器(默认 maxDelay/multiplier) + 全参重载
- `account.AccountResolver.resolve(...)` —— `(String, Map)` + `(String)` 重载

### 4.5 抽象类

- `matcher.AbstractMatcher` —— 持 `description` 字段,统一 `toString()` 实现,被 4 个具体 Matcher 继承

### 4.6 Lambda + Stream

- `matcher.Matcher.and / or / negate` —— 默认方法用 Lambda 实现链式组合
- `matcher.Matchers.all(...) / any(...)` —— `Stream.allMatch / anyMatch` 聚合
- `retry.RetryPolicy.orElse(next)` —— 返回匿名内部类(SAM 是泛型方法,Lambda 推断不到 T)

## 七、风险与权衡

| 风险 | 应对 |
|---|---|
| 深圳大学 ehall 选择器更改 | 集中在 `client/step/` 目录,失败时 `Tracer` 记录 trace_id + 截图,人工修复成本低 |
| Playwright Java 绑定不可用 | 抽象 `BrowserLifecycle` 接口隔离;`--dry-run` 短路便于单测 |
| 真实跑通预约可能违反校规 | 本项目**不绕过验证码、不高频访问**(默认重试 ≤ 3 次,见 ADR-0006);课堂演示走"项目轮换"避免重复占位 |
| 大作业评分需要可 grep 的证据 | 每个核心类首行 `// Design Pattern: XXX`,每处技术使用 `// 编程技术: XXX`,grep 即可定位 |

## 八、对外协议契约

### 8.1 CLI

```bash
szu-agent <skill> <action> [--key value ...] [--format json|human] [--env-file <path>] [--dry-run]
```

- **stdout**:JSON(默认)或人类可读文本
- **stderr**:Logback 日志(包含 trace_id)
- **退出码**:0=成功,1=业务失败,2=参数错误,3=环境/凭证错误,4=浏览器错误

### 8.2 JSON 响应 Schema(PRD §5.2)

```json
{
  "success": true,
  "data": { "venueName": "网球场1号", "confirmation": "BK-20260613-001" },
  "errorCode": null,
  "errorMessage": null,
  "traceId": "20260613-A7K2P9",
  "elapsedMs": 4321
}
```

### 8.3 MCP 协议(P1 薄壳,详见 `MCP.md`)

- `tools/list` 返回 `booking_venue` 等工具的 JSON Schema
- `tools/call` 收到请求后 fork jar 进程执行,把 stdout JSON 包装回 MCP response
